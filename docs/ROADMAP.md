# План развития: от демо к инструменту для SOC и CISO

Документ отвечает на вопрос «как обновить проект, чтобы он был реально полезен» и служит основой для issues и PR.
Сопутствующие документы: [`ARCHITECTURE.md`](./ARCHITECTURE.md) — целевая архитектура, [`SECURITY.md`](./SECURITY.md) — модель угроз и требования.

---

## 1. Критерий «реально полезен»

Сегодняшний проект — генератор текста, похожего на OSSEC-декодер. Полезным для эксплуатации он становится, когда
артефакт проходит четыре проверки:

| # | Проверка | Что это значит на практике |
|---|---|---|
| 1 | **Работает на наших логах** | правило прогнано через реальный движок (`wazuh-logtest` / `ossec-logtest`) на строках из нашего парка, а не «выглядит правдоподобно» |
| 2 | **Не увеличивает шум** | есть negative-фикстуры: доказательство, что правило не срабатывает на нормальном трафике |
| 3 | **Не дублирует существующее** | проверка коллизий ID и семантической близости с уже стоящим рулсетом |
| 4 | **Прослеживаемо** | у правила есть источник (Sigma/лог), техника ATT&CK, требования регулятора, автор, ревьюер, версия промпта и модели |

Разделение ценности по ролям:

**SOC-аналитик / инженер детекций** получает:
- конвейер «корпус логов → декодеры и правила → зелёный тест → PR», а не переписку с чат-ботом;
- отчёт «сколько наших лог-строк вообще не декодируется» — это готовый бэклог работ;
- авто-сгенерированные фикстуры, с которыми правило можно регрессионно тестировать в CI;
- генерацию одного источника Sigma сразу под несколько платформ (Wazuh/OSSEC/Splunk/Elastic), без ручного перевода;
- tuning-loop: приток false positive из алертов → предложения по корреляции/порогам.

**CISO** получает:
- покрытие в терминах, на которых говорит бизнес и аудитор: техники MITRE ATT&CK и требования регуляторов;
- метрики качества детекций (доля правил с зелёным тестом, FP-ставка, time-to-rule, стоимость правила);
- прослеживаемость и аудит: кто, когда, каким промптом и какой моделью породил правило;
- обоснование остаточного риска: непокрытые приоритетные техники как вход в risk register;
- ответ на вопрос о данных: логи не уезжают в чужое облако без классификации и маскирования (см. `SECURITY.md`).

## 3. Целевой продукт

**Detection-as-Code ассистент для SIEM-правил.**

```
корпус логов ──► анализ покрытия ──► кандидаты детекций ──► LLM-генерация ──► валидация движком ──► ревью ──► правила в прод
   (реальные)      (что не              (Sigma/эскиз)        (GigaChat,          (logtest, схема,       (PR)      + отчёты
                    декодируется)                             structured output)  коллизии ID)                    для CISO
```

Инвариант, на котором держится вся ценность: **LLM предлагает — движок проверяет.**
Ни один артефакт не попадает в прод без зелёного `logtest` и negative-фикстур. Это снимает главный риск LLM-подхода
(правдоподобный, но нерабочий результат) и делает систему защищаемой перед CISO и аудитором.

## 4. Фазы

### Фаза 0. Ремонт и гигиена — 1–2 дня

**Задачи**
1. Исправить `cli_version.py`: читать credentials из переменной окружения, убрать синтаксическую ошибку.
2. Убрать `while True` из Streamlit, перейти на `st.session_state`; добавить обработку отсутствующих секретов и понятную ошибку.
3. Вынести промпты из кода в `prompts/*.md` с версией и обычными (не экранированными) регулярками в fenced-блоках.
4. Один общий модуль вместо двух копий логики; `verify_ssl_certs` по умолчанию **True**, отключение — только явным флагом с предупреждением в лог.
5. `pyproject.toml` (PEP 621) с раздельными группами зависимостей: `runtime` (`gigachat`, `gigachain-core`, `streamlit`, `pydantic`), `validate` (парсинг XML, `defusedxml`, `pySigma`), `dev` (`pytest`, `ruff`, `mypy`). `requirements.txt` пересобрать: 112 → ~10 пакетов, добавить lock (`uv`).
6. `.gitignore`, `LICENSE`, `CHANGELOG.md`, pre-commit (`ruff`, `ruff-format`), GitHub Actions: lint + тесты + сборка образа.
7. `Dockerfile` для CLI.
8. Проверить историю git на утёкшие токены (`gitleaks`/`trufflehog`); при находке — отозвать.

**DoD:** `pip install -e ".[dev]"` работает; `ruff check` чист; CLI печатает `--help` и умеет работать на fake-провайдере; CI зелёный; в репозитории нет секретов и мёртвых зависимостей.

**Ценность:** проект можно запустить, передать коллеге и безопасно собирать.

### Фаза 1. Ядро: контракты данных и пайплайн — 3–5 дней

**Задачи**
1. Pydantic-модели (см. `ARCHITECTURE.md` §Модель данных): `LogSample`, `CoverageReport`, `DetectionCandidate`, `RuleArtifact`, `ValidationResult`, `Provenance`.
2. Провайдер LLM за интерфейсом: `GigaChatProvider` (облако/on-prem), `FakeProvider` (детерминированные ответы для тестов и CI без сети). Никаких прямых вызовов SDK из логики.
3. **Structured output**: модель возвращает JSON по схеме (`rule_id`, `description`, `level`, `decoder`, `regex`, `order`, `mitre`, `confidence`, `rationale`), а не «сделай XML как в примере». XML собирает наш сериализатор.
4. CLI: `siggen analyze`, `siggen generate`, `siggen validate`, `siggen export`, `siggen report`.
5. Кэш ответов, retry с backoff, учёт токенов и стоимости, лимиты на прогон.
6. Логирование в структурированном виде; в `Provenance` пишется модель, версия промпта, хэш входного корпуса.

**DoD:** end-to-end прогон на `FakeProvider` без сети; golden-снэпшоты выхода; покрытие тестами ядра ≥70%; артефакты детерминированы при одном входе.

**Ценность для SOC:** воспроизводимость — правило можно перегенерировать и сверить. **Для CISO:** появляется прослеживаемость (кто/чем/на основании чего).

### Фаза 2. Валидация движком — 3–5 дней

**Задачи**
1. `docker-compose.yml`: `wazuh-manager` (или урезанный `analysisd`) + runner-контейнер. Прямых правок в `/var/ossec/ruleset` нет — кандидаты подкладываются как `local_rules.xml` в изолированный инстанс.
2. Runner `wazuh-logtest`:
   - проверка «правило матчится»: `wazuh-logtest -U <rule_id:level:decoder>` → код возврата 0 (годится для одиночных автоматических проверок);
   - разбор фаз 1/2/3 (pre-decoding, decoding, rule filtering) в машинный отчёт;
   - альтернативный путь через Wazuh Server API `logtest` (JWT, `PUT` для проверки строки, `DELETE` для снятия сессии) — для интеграции без shell;
   - валидация конфигурации перед тестом: `wazuh-analysisd -t`.
3. Для OSSEC — `ossec-logtest`, тот же интерфейс runner-а.
4. Фикстуры на каждое правило: `positive/*.log` (должно сработать, ожидаемый rule id и level) и `negative/*.log` (шум — срабатывать не должно).
5. Статические проверки, не требующие движка: XML-схема и well-formedness, диапазон ID и отсутствие коллизий с существующим рулсетом, ссылки `<if_sid>` на реально существующие правила, экранирование значений, парсинг через `defusedxml` (защита от XXE), обязательный ревью для правил с `active-response`.
6. CI-gate: PR с правилом без зелёного `logtest` + negative-фикстур не мержится; отчёт logtest прикладывается к PR.

**DoD:** демонстрационный набор из 10 правил с фикстурами, прогон в CI занимает <5 минут, отчёт о валидации доступен как артефакт.

**Ценность для SOC:** правила не ломают прод. **Для CISO:** доказательство «каждое правило проверено на реальном движке» — это то, что можно показать аудитору.

### Фаза 3. Sigma как источник и мультиплатформенный экспорт — 1–3 недели

**Задачи**
1. Вход — Sigma YAML; поддержать конвертацию «свободного текста/архива правил» в Sigma как промежуточный шаг (LLM пишет Sigma, а не XML).
2. Валидация Sigma через `pySigma`: невалидный вход — явная ошибка, а не молчаливый пропуск.
3. Эмиттеры:
   - Wazuh/OSSEC XML — **собственная реализация** (официального pySigma-бэкенда для Wazuh/OSSEC не существует, см. §Риски);
   - Splunk/Elastic — существующие pySigma-бэкенды.
4. Явный маппинг полей в `field_mapping.yaml`; **неотмапленное поле — это ошибка сборки**, а не warning. Иначе получаем класс правил, которые «компилируются, но никогда не срабатывают».
5. Учёт ограничений модели Wazuh: отсутствие общей OR-логики → один Sigma может разложиться в несколько правил (DNF-разложение), связь между ними хранится в реестре ID; отдельно документировать, чего выразить нельзя (`near`-логика, timeframe-корреляции требуют композиции `<if_matched_sid>` + `frequency`/`timeframe`).
6. Автомаппинг: `tags: attack.t1078` → `<mitre><id>T1078</id></mitre>`; compliance-группы (`pci_dss`, `gdpr`, `hipaa`, `nist_800_53`, `tsc`) — управляются конфигом, а не выдумываются моделью.
7. Таблица ограничений конвертера в документации — честно, с примерами того, что не поддерживается.

**DoD:** одна Sigma-правило → правила для Wazuh и Splunk, оба проходят соответствующие валидаторы; ограничения задокументированы и покрыты тестами.

**Ценность для SOC:** один источник правды вместо ручного перевода под каждую платформу. **Стратегическая ценность проекта:** отсутствие pySigma-бэкенда для Wazuh/OSSEC — известный пробел в экосистеме.

### Фаза 4. Работа с реальными логами — 2–4 недели (главная фаза по ценности для SOC)

**Задачи**
1. **Ingest**: файлы и директории, дампы `rsyslog`/`journald`, Wazuh API (алерты), OpenSearch.
2. **Анализ покрытия**: прогнать корпус через `logtest` без пользовательских правил и посчитать, сколько строк вообще не декодируется. Кластеризация неразобранных строк (шаблоны по типу Drain3 или простой n-gram) → рейтинг «топ источников без парсинга». Это самый полезный артефакт для SOC: бэклог работ, обоснованный данными, а не догадками.
3. Генерировать детекции **только по непокрытым** кластерам; массовый анализ идёт в очередь кандидатов, а не сразу в правила.
4. **Дедупликация**: сравнение с существующим рулсетом (по полям/паттернам/технике) → вердикт «уже покрыто, генерировать не нужно».
5. **Авто-фикстуры**: положительные строки берутся из корпуса, отрицательные — из контрольной выборки нормального трафика.
6. **Tuning-loop**: выгрузка false positive из алертов Wazuh → предложения по снижению шума (корреляция, порог, suppression, уточнение regex) с тем же обязательным gate и указанием, что именно правило перестанет ловить. Удаление правила — только вручную.
7. Batch-обработка с лимитами стоимости и отчётом «принято/валидно/отклонено/стоимость».

**DoD:** на корпусе ≥100 000 строк: отчёт покрытия с разбивкой по источникам, ≥20 валидированных правил, negative-фикстуры, оценка сэкономленного времени аналитика.

**Ценность для SOC:** правила появляются там, где есть слепые зоны, и сразу с тестами. **Для CISO:** цифра «доля лог-строк под разбором» и динамика закрытия слепых зон.

### Фаза 5. Отчётность для CISO и жизненный цикл правил — 2–4 недели

**Задачи**
1. **Coverage dashboard**: heatmap MITRE ATT&CK по правилам в проде, матрица «техника × платформа», тренды во времени.
2. **Compliance mapping** (маппинг в конфиге, не в модели): PCI DSS 4.0, ISO/IEC 27001:2022 Annex A, NIST SP 800-53, CIS Controls v8, GDPR; для российского контура — 152-ФЗ, приказ ФСТЭК №17, ГОСТ Р 57580.1. Отчёт «какие требования закрыты автоматизированной детекцией». Формулировка честная: система даёт **маппинг и доказательства**, а не закрывает требование регулятора.
3. **Реестр правил и жизненный цикл**: уникальный ID, владелец, статус (`draft` → `tested` → `reviewed` → `prod` → `deprecated`), версия, дата последней проверки, ссылки на фикстуры, платформа.
4. **Audit trail**: модель, версия промпта, хэш входного корпуса, ревьюер, коммит, дата. Неизменяемый журнал.
5. **Отчёты**: Markdown/HTML/XLSX/PDF + экспорт в risk register. «Остаточный риск» = непокрытые техники из приоритетного профиля.
6. **Метрики**: покрытие техник, доля правил с зелёным тестом, FP-ставка, time-to-rule, размер бэклога, стоимость на правило.

**DoD:** отчёт для CISO генерируется одной командой из репозитория правил.

## 5. Анти-цели

- Чат-бот, который выдаёт правила «по описанию» без проверки движком. Это текущее состояние — и оно не масштабируется в эксплуатацию.
- Прямая запись в `/var/ossec/etc/rules/local_rules.xml` и `/var/ossec/ruleset` на продакшн-менеджере. Только артефакты в git + ревью + деплой.
- Генерация правил с `active-response` без отдельного процесса ревью.
- Отправка сырых логов в модель без классификации и маскирования.
- Обещание «автоматически закрываем требования регулятора».
- Поддержка «всех SIEM» на равных. Сначала платформа, для которой есть чем валидировать.

## 6. Метрики успеха

**Продуктовые**
- доля правил, прошедших `logtest` с первой итерации (цель ≥60% к Фазе 4);
- время «есть лог → правило в прод»;
- доля ложных срабатываний у сгенерированных правил после внедрения;
- количество слепых зон (неразобранных кластеров логов), закрытых за месяц.

**Для CISO**
- покрытие приоритетных техник ATT&CK;
- доля регуляторных требований, закрытых автоматизированной детекцией;
- доля правил с полной прослеживаемостью (модель, промпт, корпус, ревьюер);
- стоимость на одно правило (токены + человеко-часы);
- инциденты, обнаруженные собственными правилами, а не внешним сообщением.

## 7. Риски и открытые вопросы

| # | Риск / вопрос | Комментарий | Решение |
|---|---|---|---|
| R1 | Модель выдаёт правдоподобный, но нерабочий результат | снижается Фазой 2 (движок — источник правды) | обязательный gate |
| R2 | Нет официального pySigma-бэкенда для Wazuh/OSSEC | проверено: в каталоге плагинов pySigma и в списке related-projects бэкендов Wazuh/OSSEC нет; конвертация сложна из-за модели «base rule + `<field>`/`<if_sid>`» и отсутствия общей OR-логики | решение владельца: свой внутренний эмиттер (быстро) либо публичный pySigma-плагин (вклад в экосистему, узнаваемость, но дольше) |
| R3 | Валидация Splunk/Elastic требует живых инсталляций | конвертация проверяется только unit-тестами | либо инфраструктура для тестов, либо честно ограничить «проверено движком» до Wazuh/OSSEC |

## 9. Порядок работ

```
Фаза 0 (гигиена)  ──►  Фаза 1 (ядро)  ──►  Фаза 2 (валидация движком)
                                                │
                                                ├──► Фаза 3 (Sigma + мультиплатформа)
                                                │
                                                └──► Фаза 4 (реальные логи) ──► Фаза 5 (отчёты CISO)
```

Фазы 3 и 4 могут идти параллельно после Фазы 2. Фаза 5 без Фазы 4 даёт красивый отчёт о небольшом объеме правил — начинать её раньше осмысленно только при наличии уже накопленного рулсета.
